# Project Intelligence SOP

## Purpose

Project intelligence is an on-demand governance route for material new builds,
legacy recovery, major restructuring, unfamiliar integrations, consequential
architecture or scientific decisions, and projects whose data, resources, or
external implementations could change the next decision. It is not a routine
task ceremony. Apply the smallest investigation that can safely choose the
next bounded sprint.

Load the matching workflow skill for execution. This SOP governs when and how
to use that work; it does not prescribe a fixed sequence or duplicate the
workspace doctrine.

## Authority and scope

The Human Lead owns product, scientific, and material-risk decisions. The
Orchestrator frames the decision, selects minimum sufficient context, and
obtains needed approval. The Executor gathers bounded evidence, presents
options where a material choice remains, implements approved scope, and
verifies proportionately.

Project `AGENTS.md`, `PROJECT_STATE.md`, current direction, and relevant
contracts own project truth. A project may record a compact direction,
decision, disposition, or lock only when it has durable decision value. Git
owns history. Runtime state and temporary reference inspection are disposable.
Do not create a second authority or duplicate project memory.

## Invocation and proportionality

Begin with triage when re-foundation is material. Then select zero or more
independent intelligence tracks only if each can change the recovery or build
decision. A predecessor, local dataset, external reference, or formal plan is
never required merely because this SOP was loaded.

Use read-only parallel investigation only when tracks are independently
justified and their results will converge into one decision. One executor is
the sole writer for project artifacts and implementation.

Stop investigating when additional evidence is unlikely to change the next
decision. Prefer sufficient evidence, a recorded decision, and a bounded
sprint over repeated audit.

## Prior-art-first trigger

For a nontrivial new build, major rebuild, or re-foundation, assess early
whether external repositories, reference implementations, mature libraries,
models, datasets, benchmarks, or established workflows are likely to change
the build mode, architecture, or resource plan. When likely, select the
smallest relevant professional-reference and/or data-source discovery tracks
before material greenfield implementation. Do not infer suitability from stars
or search rank alone.

Discovery, cataloging, comparison, and deeper inspection are proportional:
capture only candidates that could change a decision, then assess the applicable
dimensions — goal fit, architecture, organization, maintenance/activity,
license and usage limits (including model weights and data), dependencies and
runtime, data availability, documentation/tests, security, extensibility,
deployment, performance, and adaptation burden. Assign the canonical
reference disposition and converge on a build direction. Skip the pass for a
trivial/disposable task, negligible expected value, or a meaningful Human Lead
from-scratch constraint.

## Decisions and exceptional gates

The recovery/build mode and any material adoption, rebuild, data, architecture,
or scientific choice must be visible to the Human Lead when approval is
required. Use Council only when consequential alternatives remain after
evidence gathering: for example repair versus rebuild, external-base adoption,
irreversible migration, scientific validity, or security/release assurance.

Formal Blueprint or freeze is exceptional, project-local, and scope-bound. It
is justified for preregistered evaluation, irreversible migration, production
release, security/privacy or regulatory boundaries, or another consequential
lock. It must state its purpose, scope, and decision owner. It is not the
default project memory or delivery plan.

## Completion

Intelligence is complete for the current cycle when the project has enough
evidence to state its current direction, select one bounded sprint, verify it,
commit it when authorized, update meaningful project state, and decide the
next sprint. Reopen an intelligence track only when a specific new question
could change that decision.
