# Technical documentation

Write for one identified reader and their next action. Ground every operational
fact in current code, contracts, or project evidence; distinguish documented
behavior from proposals and examples. Prefer a concise task flow, exact
interfaces/commands only when verified, and links to the authority that owns
volatile details.

Update existing structure rather than inventing a documentation system. Check
that the result answers the reader's likely question, names assumptions and
limits that affect safe use, and does not promote a draft into a contract.
